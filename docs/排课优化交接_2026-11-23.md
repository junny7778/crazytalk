## 二、用户最终确认的需求

### 1. 页面和教材

- 按学员排课分“一键排课”“自定义排课”。灵活排课就是自定义，不再作为一键排课下面第三种产品入口。
- 一键排课先明确本次教材、开始日期、周期、时长、每周频次及意向时间，再选老师优先/时间优先；策略一行两张简洁选项。
- 推荐采用卡片，直接显示老师资料、匹配理由、可承担节数、方案覆盖和缺口，再进入预览调整；核心信息不能大量折叠。
- 老师可授教材、学员学习教材均为多选。只在原详情信息中增加字段/标签，通过原“编辑资料”维护，不新建教材页面、Tab、独立卡片或独立编辑入口；绝不能删除、减少原有资料字段。
- 学员学习教材、本次选用教材、老师可授教材必须匹配。自动和手动都执行教材硬校验；手动不能靠“确认老师”绕过教材条件。目前按每节一本教材保存，本次多本可按课次调整。
- 自定义、按老师排课使用日历选时段和人员卡片，复用已有多选、重复、拖动、预览与确认。异常在发生步骤提示，不额外造统一异常页面。

### 2. 老师优先和时间优先

用户明确纠正过：整个方案按主老师适配优先、再比较课次数量的思路保留，不要增加组合总评分、加权模型或复杂优化框架。

- 老师优先：优先标签匹配合适老师；尽量同一老师完成。主老师覆盖不了的课次，由其他相对合适老师补上。存在合格备选时，不因“老师优先”强制留空。
- 时间优先：优先满足课次数量和时间覆盖，必要时多老师组合。
- 两者都只提供推荐，最后必须人工预览确认，确认前可以调整。无人满足硬条件时可以留缺口，但要明确显示。

### 3. ClassIn 前置条件

- 无论按学员选老师、按老师选学员，还是一键/自定义排课，老师与学员都必须已绑定 ClassIn（有已核实 UID）。
- 入口阻断、人员不可选原因、绑定后继续操作、草稿恢复和最终提交都要一致，不能只有学员概况拦截。
- 现有建班还要求负责教务存在、启用且绑定 UID；本轮把这个既有后端要求同步到前端和公共校验，并非新增教务工作流。
- 绑定复用现有表单。不要增加“演示模式/模拟账号”等强调文案。
- 保留权限、余额及占用、冲突、请假、教材、老师在职状态，以及换号/取消未完成时的业务限制。

### 4. 老师概况、已有课表和颜色

- 排课老师列表只展示在职老师，删除“在职/全部”筛选。老师展示 ID 使用8位随机纯数字，不递增；内部关联 ID 保留。
- 老师概况统计全部未取消课程的节数和分钟数，不按周统计；可授课时间内容左对齐。
- 概况下面直接看该老师已有课程：列表默认全日期，可筛选和分页；日历仅周视图，并标明老师空闲时段。下一步主操作是“为该老师排课”。
- 删除旧“查看完整课表”入口及其冗余实现，不能只藏按钮。不能同一功能周视图看单老师、日视图突然看全部老师。
- 老师中心详情课表也用周历，不用月历；学员中心/排课概况相似课表复用已有 UI。
- 列表/日历胶囊切换、周范围及左右箭头、“回到本周”、筛选样式，以用户提供的学员课表样式为准。
- 空档用普通白色，灰色用于不可安排；绿色保留给已完成课程，蓝色未开始、黄色待核实等沿用已有规则。说明统一在底部图例，不在顶部再放“浅绿色可排课”说明。
- 查看已有课程打开现有课程详情，操作沿用权限和原调课/取消入口，不把查看空格变成新排课。

### 5. 全部上课记录的最新取舍

曾讨论总课表的列表/周历，以及同一时段30节课如何聚合；用户随后明确要求“上课记录先去掉日历视图”，并要求清理代码。这是覆盖早先方案的最新决定。

当前全局课程查询入口为“上课记录”的列表（当前授权范围，含老师/学员、课程、考勤、同步等筛选）；不要自行恢复全局周历或聚合弹层。也没有因为早先讨论而新增另一个总课表菜单。单学员/单老师的周历保留。

### 算法实际顺序（供继续开发时避免误改）

1. 硬条件过滤包括教材、账号、在职、自动推荐资格/培训/少儿条件，以及 teacherFit 的阻断标签；排时再校验时间、请假、占用等。
2. 针对各主老师选择固定意向位置。老师优先的选时评分优先主老师覆盖，时间优先的选时评分优先整体覆盖；本轮保留这部分原逻辑。
3. 先分配主老师能上的课次，再补剩余可用课次。老师优先补人排序为适配→覆盖；时间优先为覆盖→适配。只从能覆盖至少一个缺口的老师中选，不重复挑无空档者。
4. 最终方案排序实际是：老师优先时先比较主老师 compareTeacherFit，然后总覆盖→主老师覆盖→老师数量更少→稳定 ID；时间优先跳过最前面的适配比较。没有新组合总分。
5. teacherMatch 沿用已有年龄/基础、性格、兴趣标签和风险规则。手动灵活模式的部分培训/年龄资格规则与自动不同，这是既有行为；本轮没有统一收紧，教材和 ClassIn 在手动中仍不可绕过。
